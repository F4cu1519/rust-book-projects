LIFETIMES EN RUST
=================

INTRODUCCIÓN
------------

Los lifetimes son una característica única de Rust que garantiza la seguridad de memoria
sin necesidad de un garbage collector. Son parte del sistema de ownership de Rust y
aseguran que todas las referencias sean válidas.

Un lifetime es el alcance durante el cual una referencia es válida. El compilador usa
lifetimes para verificar que todas las referencias prestadas (borrows) sean válidas y
para prevenir referencias colgantes (dangling references).


¿QUÉ SON LOS LIFETIMES?
-----------------------

DEFINICIÓN:
Un lifetime es una construcción que el compilador usa para garantizar que las referencias
vivan lo suficiente.

PROPÓSITO:
- Prevenir referencias colgantes (dangling references)
- Garantizar que los datos referenciados existan mientras se usen
- Permitir que el compilador verifique la seguridad de memoria en tiempo de compilación

CONCEPTO CLAVE:
Los lifetimes NO cambian cuánto tiempo viven los valores. Solo describen las relaciones
entre los lifetimes de diferentes referencias.


EL PROBLEMA QUE RESUELVEN
--------------------------

CÓDIGO PROBLEMÁTICO (no compila):

    {
        let r;
        {
            let x = 5;
            r = &x;  // ERROR: x no vive lo suficiente
        }
        println!("r: {}", r);  // x ya no existe aquí
    }

PROBLEMA: r intenta referenciar x, pero x deja de existir antes de que r se use.

SOLUCIÓN DEL COMPILADOR: Borrow checker
El borrow checker compara los lifetimes y detecta este problema en tiempo de compilación.


SINTAXIS DE LIFETIMES
----------------------

Las anotaciones de lifetime comienzan con un apóstrofo (') seguido de un nombre,
usualmente en minúsculas y muy corto.

CONVENCIONES:
- 'a es el más común (de "lifetime a")
- 'b, 'c, etc. para múltiples lifetimes
- Nombres descriptivos como 'static, 'input, 'output son raros pero válidos

SINTAXIS:

    &i32           // una referencia sin lifetime explícito
    &'a i32        // una referencia con lifetime explícito 'a
    &'a mut i32    // una referencia mutable con lifetime 'a


LIFETIMES EN FUNCIONES
-----------------------

PROBLEMA SIN LIFETIMES:

    fn longest(x: &str, y: &str) -> &str {
        if x.len() > y.len() {
            x
        } else {
            y
        }
    }
    // ERROR: expected named lifetime parameter

SOLUCIÓN CON ANOTACIONES:

    fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
        if x.len() > y.len() {
            x
        } else {
            y
        }
    }

SIGNIFICADO:
- El valor de retorno vivirá al menos tanto como el lifetime más corto entre x e y
- Todos comparten el mismo lifetime 'a
- El compilador verificará que se cumpla esta restricción

USO:

    let string1 = String::from("long string");
    let string2 = String::from("xyz");
    
    let result = longest(string1.as_str(), string2.as_str());
    println!("The longest string is {}", result);  // OK


EJEMPLO QUE FALLA:

    let string1 = String::from("long string");
    let result;
    {
        let string2 = String::from("xyz");
        result = longest(string1.as_str(), string2.as_str());
    }
    println!("The longest string is {}", result);  // ERROR
    
ERROR: string2 no vive lo suficiente. result podría estar referenciando string2,
que sale del scope antes de ser usada.


DIFERENTES LIFETIMES EN PARÁMETROS
-----------------------------------

No todos los parámetros necesitan el mismo lifetime:

    fn first_word<'a, 'b>(x: &'a str, y: &'b str) -> &'a str {
        x  // Siempre retornamos x, no importa el lifetime de y
    }

O simplificado (y se infiere):

    fn first_word<'a>(x: &'a str, y: &str) -> &'a str {
        x
    }


LIFETIMES EN STRUCTS
---------------------

Un struct puede contener referencias, pero necesita anotaciones de lifetime:

    struct ImportantExcerpt<'a> {
        part: &'a str,
    }

SIGNIFICADO:
Una instancia de ImportantExcerpt no puede vivir más que la referencia que contiene.

USO:

    let novel = String::from("Call me Ishmael. Some years ago...");
    let first_sentence = novel.split('.').next().expect("Could not find a '.'");
    let i = ImportantExcerpt {
        part: first_sentence,
    };
    // i es válido aquí porque novel todavía existe


EJEMPLO QUE FALLA:

    let i;
    {
        let novel = String::from("Call me Ishmael.");
        let first_sentence = novel.split('.').next().unwrap();
        i = ImportantExcerpt {
            part: first_sentence,
        };
    }
    // ERROR: novel (y por tanto first_sentence) sale del scope
    println!("{}", i.part);


LIFETIMES EN MÉTODOS
---------------------

DEFINICIÓN DE MÉTODOS:

    impl<'a> ImportantExcerpt<'a> {
        fn level(&self) -> i32 {
            3
        }
    }

REGLA: El <'a> después de impl es necesario para indicar que estamos implementando
métodos para ImportantExcerpt<'a>.

MÉTODOS CON REFERENCIAS:

    impl<'a> ImportantExcerpt<'a> {
        fn announce_and_return_part(&self, announcement: &str) -> &str {
            println!("Attention please: {}", announcement);
            self.part
        }
    }

Por las reglas de elisión (ver abajo), este método no necesita anotaciones explícitas.
El lifetime del retorno es el de &self.


REGLAS DE ELISIÓN DE LIFETIMES
-------------------------------

Rust aplica reglas determinísticas para inferir lifetimes automáticamente:

REGLA 1: Cada parámetro de referencia obtiene su propio lifetime
    fn foo(x: &i32)           → fn foo<'a>(x: &'a i32)
    fn foo(x: &i32, y: &i32)  → fn foo<'a, 'b>(x: &'a i32, y: &'b i32)

REGLA 2: Si hay exactamente un parámetro lifetime de entrada, ese lifetime se asigna
         a todos los parámetros de salida
    fn foo(x: &i32) -> &i32   → fn foo<'a>(x: &'a i32) -> &'a i32

REGLA 3: Si hay múltiples parámetros lifetime de entrada, pero uno es &self o &mut self
         (método), el lifetime de self se asigna a todos los parámetros de salida
    fn method(&self, x: &str) -> &str  → lifetime del retorno es el de &self


EJEMPLOS DE ELISIÓN:

    // No necesita anotaciones (Regla 2)
    fn first_word(s: &str) -> &str { ... }
    
    // No necesita anotaciones (Regla 3)
    impl<'a> Example<'a> {
        fn method(&self) -> &str { ... }
    }
    
    // SÍ necesita anotaciones (no aplica ninguna regla automáticamente)
    fn longest(x: &str, y: &str) -> &str { ... }  // ERROR


LIFETIME 'static
----------------

'static es un lifetime especial que significa "durante toda la ejecución del programa".

USO PRINCIPAL: String literals

    let s: &'static str = "I have a static lifetime.";

Los string literals están embebidos en el binario del programa y siempre están disponibles.

ADVERTENCIA:
No uses 'static solo para hacer que el código compile. Usualmente indica un problema
de diseño. Solo úsalo cuando realmente necesites una referencia que viva para siempre.


TRAIT BOUNDS CON LIFETIMES
---------------------------

Puedes combinar trait bounds y lifetimes:

    fn longest_with_an_announcement<'a, T>(
        x: &'a str,
        y: &'a str,
        ann: T,
    ) -> &'a str
    where
        T: Display,
    {
        println!("Announcement! {}", ann);
        if x.len() > y.len() {
            x
        } else {
            y
        }
    }

COMPONENTES:
- 'a: lifetime genérico
- T: tipo genérico
- T: Display: trait bound


LIFETIME BOUNDS
---------------

Un tipo puede tener un lifetime bound que restringe cuánto debe vivir:

    struct Ref<'a, T: 'a> {
        reference: &'a T,
    }

SIGNIFICADO: T: 'a indica que todos los parámetros de lifetime de T deben sobrevivir 'a.

NOTA: En Rust 2018+, esto se infiere automáticamente, así que raramente necesitas escribirlo.


MÚLTIPLES LIFETIMES
-------------------

Puedes tener múltiples lifetimes diferentes:

    struct DoubleRef<'a, 'b> {
        first: &'a str,
        second: &'b str,
    }

    fn compare<'a, 'b>(x: &'a str, y: &'b str) -> &'a str {
        if x.len() > y.len() {
            x
        } else {
            x  // Siempre retornamos x, no y
        }
    }


SUBTYPING DE LIFETIMES
----------------------

Un lifetime 'a es un subtipo de 'b si 'a vive al menos tanto como 'b:

    fn choose<'a, 'b>(first: &'a str, second: &'b str, choice: bool) -> &'a str
    where
        'b: 'a,  // 'b vive al menos tanto como 'a
    {
        if choice {
            first
        } else {
            second  // OK porque 'b: 'a
        }
    }


CASOS DE USO COMUNES
--------------------

1. FUNCIONES QUE RETORNAN REFERENCIAS:
    fn first<'a>(list: &'a [i32]) -> &'a i32 {
        &list[0]
    }

2. STRUCTS QUE ALMACENAN REFERENCIAS:
    struct Parser<'a> {
        text: &'a str,
        position: usize,
    }

3. ITERADORES PERSONALIZADOS:
    struct Split<'a> {
        remaining: &'a str,
        delimiter: char,
    }

4. CACHE DE REFERENCIAS:
    struct Cache<'a, T> {
        data: &'a T,
        computed: Option<String>,
    }


ERRORES COMUNES Y SOLUCIONES
-----------------------------

ERROR: "expected named lifetime parameter"
SOLUCIÓN: Agregar anotaciones de lifetime a la función

ERROR: "lifetime may not live long enough"
SOLUCIÓN: Verificar que las referencias vivan lo suficiente

ERROR: "borrowed value does not live long enough"
SOLUCIÓN: Extender el scope del valor prestado o cambiar el diseño

ANTI-PATRÓN: Agregar 'static a todo
SOLUCIÓN: Entender los lifetimes reales de tus datos


LIFETIMES Y CLOSURES
--------------------

Los closures también tienen lifetimes implícitos:

    fn make_adder<'a>(x: &'a i32) -> impl Fn(i32) -> i32 + 'a {
        move |y| x + y
    }

El + 'a indica que el closure retornado puede vivir hasta 'a.


HIGHER-RANKED TRAIT BOUNDS (HRTB)
----------------------------------

Para situaciones avanzadas donde necesitas lifetimes más flexibles:

    fn apply<F>(f: F)
    where
        for<'a> F: Fn(&'a str) -> &'a str,
    {
        // ...
    }

El for<'a> introduce un lifetime que funciona para cualquier lifetime posible.


RESUMEN Y PUNTOS CLAVE
-----------------------

✓ Los lifetimes garantizan que las referencias sean válidas
✓ Previenen referencias colgantes en tiempo de compilación
✓ Las anotaciones describen relaciones, no cambian lifetimes reales
✓ La sintaxis es 'a, 'b, etc.
✓ Tres reglas de elisión permiten omitir anotaciones en muchos casos
✓ 'static es un lifetime especial para toda la ejecución
✓ Los structs con referencias necesitan lifetimes
✓ Combinar con generics y traits es común y poderoso

CUÁNDO NECESITAS ANOTACIONES:
- Funciones que retornan referencias de parámetros
- Structs que contienen referencias
- Cuando las reglas de elisión no aplican
- Traits con referencias

CUÁNDO NO LAS NECESITAS:
- Las reglas de elisión cubren tu caso
- No trabajas con referencias
- Usas tipos owned en lugar de referencias


CONSEJOS PRÁCTICOS
-------------------

1. Comienza sin anotaciones y deja que el compilador te guíe
2. Usa owned types (String vs &str) cuando los lifetimes sean problemáticos
3. Lee los mensajes de error - son muy informativos
4. Practica con ejemplos simples antes de casos complejos
5. No agregues 'static solo para compilar

PRÓXIMOS PASOS:
- Practicar con funciones y structs que usan referencias
- Estudiar trait objects y sus lifetimes
- Aprender sobre Rc<T> y Arc<T> para casos avanzados
- Explorar patrones de diseño que minimizan lifetimes complejos
